# Phase 4.1 — Binary frames (L1): scope & implementation plan

- **Status:** SCOPED (design only, not implemented) — 2026-05-31
- **Supersedes:** the roadmap's earlier "⛔ BLOCKED — relay not in this repo" note, which was **factually wrong**. The relay *is* in this repo at `packages/relay/` (`@nudge/relay`, a Node/TS service; see `docs/relay-hosted.md:5`). 4.1 is not blocked by an external dependency — it is a non-trivial cross-component change that we can fully implement here, gated only on on-device verification (daemon/relay stack down this session).
- **Finding:** L1 — "base64-in-JSON-in-WS, doubled under E2E" (`lib.rs:3454`, `e2e.rs:185`).

## TL;DR

Terminal bytes are base64-encoded **twice** on the way to the phone, then carried as a JSON **text** frame:

1. raw bytes → `bytesBase64` (1.333×) inside an inner JSON `daemon_response`,
2. that JSON is E2E-encrypted → ciphertext → `ciphertextBase64` (another 1.333×) inside the `e2e_envelope` JSON,
3. wrapped in `{toDeviceId, ephemeral, payload}` and sent as a WebSocket **text** frame; the relay re-serializes it as JSON to the phone.

Net: **≈1.78× byte amplification** for a burst of N bytes, plus a fixed **~300–400 bytes of JSON/base64 structure per frame** (which dominates small frames like keystroke echo).

There are **two independent levers**, and they should be treated as separate sub-phases:

| Lever | What changes | Components | Wire (N bytes) | Risk |
|---|---|---|---|---|
| **A — binary plaintext** | encrypt raw bytes (+ small header) instead of JSON-with-`bytesBase64` | daemon + phone (**relay untouched**) | ~1.78N → **~1.33N** | **Low–Med** |
| **B — WS binary frames** | send the ciphertext as a WS *binary* frame instead of base64-in-JSON-text | daemon + **relay** + phone | ~1.33N → **~1.0N** + drops the fixed per-frame JSON | **High** |

**Recommendation:** do **Level A first**. It captures the larger relative win on bursts, is daemon↔phone only (the relay never sees plaintext, so its auth/routing/E2E-enforcement core is untouched), and is fully **unit-testable offline** (encrypt/decrypt round-trip on both sides). Treat **Level B** as a follow-up justified by an on-device measurement showing per-frame JSON overhead still hurts small-frame latency — it touches the relay's security core and must replicate every check.

## Current end-to-end path (verified, with refs)

### Daemon → wire (Rust)
- `flush_pending_terminal_outputs` (`crates/nudge-daemon/src/lib.rs:3272`) builds, per tab, either a snapshot or a delta.
- Delta payload: `relay_live_terminal_output_payload` (`:3380`) → `terminal_output_json` (`:3447`):
  ```json
  {"type":"daemon_response","bindingId":"…","ok":true,
   "data":{"tabId":"…","offset":<u64>,"bytesBase64":"<base64(raw bytes)>"}}
  ```
- `relay_live_payload` (`:3334`) E2E-encrypts that JSON **string**: `session.keys.encrypt("daemon_live_terminal", payload.to_string().as_bytes())` (`:3348`).
- `e2e::envelope_to_relay_payload` (`crates/nudge-daemon/src/e2e.rs:176`):
  ```json
  {"type":"e2e_envelope","sessionId":"…","senderDeviceId":"…","recipientDeviceId":"…",
   "messageType":"daemon_live_terminal","sequence":"…",
   "nonceBase64":"<b64(12B)>","ciphertextBase64":"<base64(ciphertext)>"}
  ```
  AAD binds `sessionId|sender|recipient|messageType|sequence|nonce` (`e2e.rs:95-102`), so **`messageType` is authenticated** — usable as a format discriminator.
- `relay_message_json` (`:3168`) → `{"toDeviceId":"…","ephemeral":true,"payload":<envelope>}` → `WebSocketMessage::Text` (`:3318`).

### Relay (TypeScript, `packages/relay/src/index.ts`)
- Inbound: `websocket.on('message', (bytes) => { JSON.parse(bytes.toString()) })` (`:768-771`) — **assumes every frame is JSON text**; a raw binary frame UTF-8-decodes to garbage and fails → `invalid_json`.
- Routing/auth, all read from the **cleartext outer JSON** (never the ciphertext):
  - binding active (`:776`), sender device active (`:781`),
  - **route authorization**: `isBindingParticipant(binding, message.toDeviceId) && toDeviceId !== self` (`:786`),
  - target device active (`:790`),
  - `validateRelayPayload(message.payload, …)` (`:794`): in hosted mode `requireE2EPayload` is forced on (`docs/relay-hosted.md:104`), so the payload **must** be `type==='e2e_envelope'` with non-empty `sessionId/sender/recipient/messageType/sequence/ciphertextBase64/nonceBase64` (`validateE2EEnvelope`, `:941`).
- Forward: `targetSocket.send(JSON.stringify({type:'message', message: relayMessage}))` (`:817`); audit `message_routed`; if the target socket is closed and the message is **not** ephemeral, it is **queued** (`:825-828`); sender gets `{type:'accepted', messageId}` (`:837`).
- The relay **never decrypts** (`docs/relay-hosted.md:16`) — the ciphertext (`payload`) is opaque to it.

### Wire → phone (Swift, `RelayClient.swift`)
- Receive loop already branches on frame type: `case .string` / `case .data` (`:591-595`).
- `decodeDaemonPayload` (`:1011`): requires `rawPayload.type == "e2e_envelope"` (`:1015`), `decrypt(envelope)` (`:1022`) → plaintext **Data**, then JSON-decodes it.
- Inner terminal output: `TerminalOutput.bytesBase64` (`:472`) → `Data(base64Encoded:)` (`:479`).
- Phone → daemon uses the symmetric path: `session.encrypt(messageType, plaintext)` (`:1003`).

### Cost accounting (N raw bytes, ChaCha20Poly1305 +16B tag, base64 = 4/3)
```
raw N
 → bytesBase64        ≈ 1.333·N      (+ inner JSON ~90B fixed)
 → ciphertext         ≈ 1.333·N + ~106B            (encrypt of inner JSON)
 → ciphertextBase64   ≈ 1.78·N + ~140B             (+ envelope JSON ~200B fixed)
 → outer + relay re-serialization (toDeviceId, message wrapper, ids, createdAt)
```
- **Large burst** (e.g. `cat` a file): dominated by the **1.78× multiplier** → Level A (kills one 1.333×) helps most.
- **Small frame** (keystroke echo, a few bytes): dominated by the **fixed ~300–400B JSON/base64 structure** → only Level B (compact binary frame) removes it; this is the latency-sensitive case.

## Level A — binary plaintext (daemon + phone; relay untouched)

**Idea:** the relay can't see plaintext, so the *inner* format is a private daemon↔phone contract. Replace the JSON-with-`bytesBase64` plaintext (for the high-volume terminal-delta path only) with a compact binary plaintext, then encrypt that.

**Plaintext layout (proposed):**
```
magic  u8   = 0x01            // format/version; rejects accidental JSON-vs-binary confusion
kind   u8   = 0x01 delta | 0x02 snapshot
offset u64  (LE or varint)
tabId  len-prefixed UTF-8 (u16 len + bytes)
data   raw terminal bytes (delta) — to EOF
```
- **Daemon:** add `relay_live_terminal_output_payload` binary variant; encrypt with a distinct `messageType` (e.g. `"daemon_live_terminal_bin"`) so the discriminator is AAD-authenticated. Keep `envelope_to_relay_payload` exactly as-is (still `ciphertextBase64` JSON) — the relay sees no change.
- **Phone:** in `decodeDaemonPayload`, branch on `envelope.messageType`: the `_bin` type decrypts to bytes parsed by the layout above (no JSON), feeding the same `applyTerminalDelta`/`applyTerminalSnapshot`.
- **Relay:** **no change.** Still a valid `e2e_envelope`; passes `validateE2EEnvelope`.

**Savings:** ~1.78N → ~1.33N on bursts (drops the inner base64). Does **not** reduce per-frame envelope overhead.

**Required: capability negotiation.** An old phone receiving `messageType=_bin` would try to JSON-parse binary → fail → drop the delta → gap → snapshot request (snapshots can stay JSON), but it would then *never* get live deltas → effectively broken. So the daemon must only emit binary plaintext when the phone has advertised support. Cheapest hook: a capability flag in the E2E handshake (`e2e_handshake_finish`) or the binding metadata. **This negotiation is the real design work of Level A**, not the encoding.

**Verification (offline, now):**
- Rust: `encrypt(_bin plaintext)` → `decrypt` → byte-exact round-trip; layout parse unit tests.
- Swift: decode-binary-plaintext unit test mirroring the layout; fuzz vs the JSON path for equivalence.
- On-device (later): burst bandwidth before/after; render correctness.

**Risk:** Low–Med. Blast radius is daemon↔phone. Main hazards: (1) format/version skew if negotiation is wrong (mitigated by `magic`+`messageType` AAD + the snapshot-fallback), (2) deciding whether snapshots also go binary (recommend: **delta only** first — snapshots are infrequent and JSON keeps them debuggable).

## Level B — WS binary frames (daemon + relay + phone)

**Idea:** stop base64-ing the ciphertext and stop wrapping it in JSON text; send a WS **binary** frame carrying a compact framed envelope.

**Binary frame layout (proposed):** a header carrying everything the relay routes/enforces on today, then raw ciphertext:
```
ver       u8
toDeviceId   len-prefixed UTF-8     // relay routing (was message.toDeviceId)
sessionId    len-prefixed UTF-8     // \
senderId     len-prefixed UTF-8     //  | were the e2e_envelope JSON fields
recipientId  len-prefixed UTF-8     //  | (relay validates presence/shape)
messageType  len-prefixed UTF-8     // /
sequence  u64
nonce     [12]u8
flags     u8  (bit0 = ephemeral)
ciphertext   raw bytes — to EOF     // was ciphertextBase64
```

- **Daemon:** send `WebSocketMessage::Binary(framed)` for the delta path.
- **Relay (the hard part):** `websocket.on('message', (bytes, isBinary) => …)` — when `isBinary`, parse the header and run the **same** checks as the JSON path, in the same order: binding active, sender active, `isBindingParticipant(toDeviceId)` + not-self, target active, and an `validateE2EEnvelope`-equivalent on the parsed header (hosted-mode `requireE2EPayload`). Then re-frame and `targetSocket.send(<binary>, {binary:true})`; preserve audit (`message_routed`/`rejected`), the **non-ephemeral queue** path (`:825`), and the `{type:'accepted'}` ack (which can stay a JSON control frame). Add `check:relay-container`/smoke coverage.
- **Phone:** already receives `.data` frames (`RelayClient.swift:595`) — add a binary-envelope decoder; everything downstream is unchanged.

**Savings:** ~1.33N → ~1.0N **and** removes the fixed per-frame JSON (~300–400B) — the win for small/latency-sensitive frames.

**Risk: High.** The relay's entire security posture (route auth, E2E enforcement, replay/sequence semantics, audit, queueing, rate limits) is currently expressed over JSON fields. A second binary path must replicate **all** of it or it becomes a bypass. Plus: backward-compat (an old relay drops/errors binary frames → hard requirement for capability negotiation across all three parties), and mixed text/binary handling on every socket. Combine with Level A's binary plaintext for the full ~1.0N.

## Risk register

| # | Risk | Lever | Sev | Mitigation |
|---|---|---|---|---|
| 1 | Old phone can't parse binary plaintext → silently loses live deltas | A | High | Capability negotiation in handshake; daemon emits binary only when advertised; snapshots stay JSON as a floor |
| 2 | Binary relay path skips a security check present on the JSON path (auth bypass) | B | Crit | Factor the JSON checks into one function reused by both paths; smoke test each rejection (`route_not_authorized`, `e2e_payload_required`, revoked, replay) on the binary path |
| 3 | Old relay drops/error-closes binary frames | B | High | Tri-party capability negotiation; fall back to text path if relay lacks the capability |
| 4 | Mixed text/binary on one socket (control = text, deltas = binary) confuses framing | B | Med | Explicit `isBinary` branch; keep all control + acks as text |
| 5 | Non-ephemeral queue / replay-sequence semantics differ between paths | B | Med | Reuse the same `RelayMessage` construction + queue logic; only framing differs |
| 6 | Can't verify on real device this session (stack down) | A+B | Med | Land the offline unit tests now; gate the on-device bandwidth/CPU benchmark + render check |

## Verification plan
- **Offline (this repo, now):** Rust encrypt/decrypt + layout round-trip (Level A); relay binary-route smoke tests mirroring the JSON rejection matrix (Level B), in the existing `packages/relay/src/smoke-*.ts` style; Swift decode unit tests.
- **On-device (stack up):** burst bandwidth + CPU (`cat` a large file) before/after; single-keystroke echo latency (Level B's target); visual correctness.

## Recommendation
1. **Level A** (binary delta plaintext + capability negotiation) — most of the burst win, contained blast radius, offline-testable. Ship behind the negotiated capability.
2. **Level B** (WS binary frames) — only if an on-device measurement shows per-frame JSON overhead still hurts small-frame latency. Budget for careful relay security-parity work + tri-party negotiation.

Either way the earlier "blocked — relay not in this repo" framing is retired: this is implementable here; the gate is on-device verification, not external access.
